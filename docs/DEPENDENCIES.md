# Dependency ownership and exposure

The root `package.json` owns the supported controller's exact runtime dependency set, Node 24 engine and CommonJS format. `deployment/deployment-package.json` must mirror it; its independent production lock is staged as the controller's `package-lock.json`. Root tooling and private webhook/cleanup workspaces exercise tests and compatibility wrappers. Their manifests are not independent deployment entry points. The two source-reference locks remain separate offline qualification contexts.

`npm run check:dependencies` checks ownership/parity and the generated [four-lock inventory](../deployment/dependency-inventory.json). `npm run check:archive` also enforces runtime manifest parity before packaging. Extra runtime declaration channels cannot silently bypass the canonical dependency set. Packaging receipts bind the new checker and every root/workspace manifest it reads, in addition to their existing source/lock bindings.

The inventory contains fixed lock paths/hashes, roles, all direct runtime declarations, and relevant package occurrences at their physical nested lock locations. Immediate owner edges retain runtime/optional/peer kinds; representative shortest root paths distinguish production, tooling, compatibility and reference reachability. This is declared lock reachability, not proof that a vulnerable API executes. Shared hoisted packages can serve several contexts. Never classify a dependency solely from `dev: false` or use one global name-to-version map.

After an intended lock change, run `node scripts/dependency-inventory.cjs --write`, review the source facts, and run `npm run check:dependencies`. Generation is offline and does not install, dismiss alerts or produce advisory judgments. Refresh the separately authored [dated assessment](../deployment/dependency-status.json) against the new lock hashes and current public advisories; checks reject an assessment bound to different locks. Do not replace historical observations with claims that a new revision was tested.

## Independent installation evidence

`python3 scripts/qualify-source-profile.py` now first invokes `scripts/qualify-standalone.py`, then qualifies both reference closures. The standalone helper stages only controller inputs outside the repository, runs `npm ci --ignore-scripts --engine-strict`, verifies the lock is unchanged, and checks SDK APIs, Functions Framework registration and disabled routes. Every runtime dependency must resolve inside that fresh installation; `NODE_PATH`/`NODE_OPTIONS` are removed. A refusal test proves populated root modules cannot satisfy a missing standalone install.

These checks establish source/install contracts with no provider calls. They do not establish live IAM, ingress behavior, private networking, App/JIT lifetime, an image boot or a vulnerability-free installation. Reassess the dated API conclusions when owners, APIs, trust boundaries or advisories change.
